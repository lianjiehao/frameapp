# Architecture

[English](architecture.md) | [简体中文](architecture.zh-CN.md)

## Read the code in this order

1. [main.dart](../lib/main.dart): app startup, consent integration and camera screen.
2. [CameraCoach](../lib/services/coach.dart): a `ChangeNotifier` coordinating phases, camera lifecycle, analysis and capture. The screen listens to its state.
3. [core](../lib/core/): pixel normalization, selected-subject tracking, scene evidence, composition ranking and stability.
4. [platform services](../lib/services/): conditional native/Web photo capture, saving and local policy rendering.

~~~text
Image input
  → pixel_buffer: orientation, mirror, centered 3:4 crop
  → GrayFrame: tracking at 192×256; scene analysis at 96×128
  → subject_tracking + vision + scene_evidence
  → composition: rank options, choose target, evaluate stability
  → CameraCoach → main.dart + ui/guides.dart
  → camera_photo → gallery (native album / Web download)
~~~

The composition flow in `coach.dart` is `framing → recommending → guiding → ready → capturing → captured`; subject selection completes asynchronously within the current phase. Direct capture, reset, retry, suspension and lost tracking branch from this flow; inspect the controller before changing transitions. Native camera sampling, subject selection and analysis share one `compute` job, with requests throttled to about 120 ms and only the latest pending frame retained with its original time. The camera crop is area-averaged before reduction to 192×256 so fine foliage does not turn into aliasing noise during small movements. The controller publishes the sampled frame together with its analysis; an expired result cannot restore a live lock or shutter readiness.

On native builds, practice mode opened from Help or the camera error view has an Exit practice button in the header. Exiting cancels practice sampling, clears the selection and composition guidance, then returns through the existing consent and camera-permission checks. A previous permission rejection still requires the explicit camera retry. Web and `DEMO_MODE=true` builds remain practice-only. Practice exposes only Composition mode; entering practice from Pose resets to Composition, and exiting restores the native Pose tab. `practice_mode_test.dart` covers entering from Help, exiting during guidance, cleanup, permission rejection and compact headers; native camera restoration still needs device verification.

`ui/camera_help.dart` presents the guide as three numbered steps, followed by quieter shooting tips. Its full-width practice button sits in a separate footer below the scrollable content, keeping it reachable on short screens and with larger text. The privacy shortcut stays in the header; practice mode hides the practice entry.

## Reference-image pose mode

Composition remains the cold-launch default. Pose uses a manual reference overlay without body detection, dashed templates or action scoring. The detector modules and their isolated tests remain available, but CameraCoach does not activate or submit frames to them. Both modes share the camera, filters, save retry and privacy gate.

ReferenceLibrary coordinates explicit system picking, normalization, SHA-256 deduplication, local favorites and a bounded recent library. Bundled JPEG references and category/gender metadata need no server; catalog favorites remain separate from personal imports. Native I/O stays behind the conditional reference_store import; Web uses session memory and remains practice-only. ReferenceOverlay is a clipped viewfinder-only layer using `BoxFit.fitHeight` with centered alignment, preserving aspect ratio and adapting to preview size. Opacity and mirroring never enter photo rendering. Selection immediately exposes the shutter and moves filters into More, without positioning, scaling, reset or locking steps; preview gestures directly control rear-camera zoom when `CameraCoach.canZoom` permits it. See [behavior, storage and verification](pose.md).

Composition labels its three steps Frame, Compose and Take photo. Pose labels its steps Select image, Pose and Result. Both step rows keep the same vertical position across phases. The recommendation footer places suitability on one line beside the composition name; tapping that name and chevron opens all compositions with their full reasons. The reason is one line with a tooltip, and the top three choices place names and scores side by side in a horizontally scrollable row for narrow screens or larger text. Low-suitability and close-score explanations remain visible. The recommendation preview starts 16 pixels below the step row’s existing bottom padding and takes the largest 3:4 size that fits the remaining height after the natural footer, so short screens and larger text shrink the preview instead of crowding the footer. Other phases retain the centered preview and natural footer height. A camera zoom request during the recommendation or alignment step keeps that step active, preserves the selected composition while the subject reacquires, and refreshes the recommendation from the next frame. It reserves no shared footer height for Pose. Text tabs in the header select Composition mode or Pose mode with a short underline; flash and Help remain in the More menu. Both modes vertically center their step labels with 8 pixels of padding above and below, and connect adjacent steps with matching horizontal lines. Selecting a reference immediately enters Pose for the person to follow it and shoot. Only a captured result activates Result. Retaking preserves the selected reference and returns to Pose.

Pose fits the selected reference to the preview height and centers it horizontally. After selection, the main shutter captures immediately without body detection, an alignment hold or a separate Direct capture button. The upper row has two separate bordered areas: a reference thumbnail with a switch icon, and opacity with mirroring. There is no eye button; zero opacity hides the overlay. Restart, the centered shutter and a latest-photo icon share the lower row. Filters remain on the initial page and move into More after selecting a reference. Restart clears only the selection. The initial Pose page shares Composition’s footer spacing, filter display and rear-camera zoom controls. References never enter the photo. Composition keeps its one-second alignment requirement; Direct capture appears below the shutter only while not ready, and the right side shows the photo icon on a real camera or Auto-align in practice mode.

Pose uses the same `CameraZoomDial` as Composition both before and after reference selection: preset taps, the sliding dial and preview pinching change the real rear-camera zoom within its supported range. This is zoom, not tap autofocus; the change introduces no autofocus interaction. `CameraCoach.canZoom` requires an initialized, non-practice rear camera and an available zoom range. Front cameras, practice images and Web expose no invented zoom values. Reference tools continue to affect only the overlay, while filters and zoom affect the shared camera and clean capture path.

Reference selection stays in a bottom library sheet; cancelling it preserves the current reference. Category, gender and favorites filters stay above the independently scrolling reference-image feed; changing a filter returns the feed to the top. Both modes expose photo viewing on the result screen. Pose also exposes the latest shot beside the shutter after reference selection, without clearing the reference or its adjustments; Composition also keeps the latest-shot icon beside the shutter on the real-camera guidance screen; practice mode uses this position for Auto-align. `ui/photo_viewer.dart` displays that result across the full viewport with pinch zoom, close and system back; withdrawing consent closes the viewer. Saving failures keep the captured bytes for retry. `ui/pose_import_hint.dart` anchors a floating arrow bubble to the import button, with a single entrance animation that respects reduced motion. Its local flag is written only after display; dismissing, importing or opening another panel hides the tip.

## Selected-subject tracking

Every explicit preview tap queues selection on the same background worker as live tracking, including taps on a fresh frame. Corner extraction, template capture and pyramid construction stay off the native UI isolate. A pending tap takes priority over tracking the old subject; only the latest tap and latest pending frame survive. Expired samples cannot seed a lock, and obsolete worker results or errors cannot replace the new selection. Reset, zoom adjustment, capture and suspension cancel the queued tap. A recovered selection starts a new stability hold. A low-detail selection uses the existing preview and footer hints without publishing an additional error message.

The worker publishes the selected subject, frame, scene features and evidence together. Recommendation ranks this already verified, fresh result; it does not launch another analysis job or pause incoming frames. Reselecting during guidance refreshes plans from that same worker result and preserves the chosen method. `composition_worker_test.dart` guards against pixel sampling on the UI isolate and covers rapid taps, expired selection results and cancellation; these are regression checks, not device performance measurements.


Short local flow first checks corners near their last verified positions. Only an insufficient local consensus falls back to whole-frame motion prediction for larger pans, preventing repeated keys or text rows from pulling the box to a distant lookalike. Local corner consensus predicts movement, then a larger patch around the actual clicked point refines its position with forward/backward flow and an appearance check. This avoids accumulating anchor drift when nearby corners shift under perspective, autofocus blur or exposure changes. Verified corners are replenished around the current anchor in a bounded screen region so zoom does not expand the search into distant background. The fixed selection template remains unchanged; occlusion and an out-of-view subject still revoke the visible lock.

Each analyzed frame and tracking snapshot carries its camera zoom. After zoom changes, the worker reprojects the previously verified pixels, anchor and corners through the centered crop before matching the new image. Newly revealed borders are excluded from whole-frame motion prediction. A close match to the original template at the new scale corrects accumulated resampling offsets; a predicted location alone never restores tracking. The old box and readiness are withdrawn as soon as a zoom request starts. Tests include known perspective transforms, repeated keyboard textures, real pixel scaling in both directions, selection at a non-default zoom, occlusion, and an aligned subject near the box edge reaching and retaining readiness.

## Camera zoom

Each rear-camera initialization reads the device’s actual minimum and maximum zoom. Three distinct quick stops are planned across the logarithmic range and rounded down to familiar values, with a minimum/midpoint/maximum fallback for narrow ranges. For example, 1–10× gives 1 / 2 / 4, while 1–20× gives 1 / 2 / 6. Unsupported presets are omitted. The live value occupies the first slot below the second stop, the middle slot below the third stop, and the last slot from the third stop onward. Thus a 1 / 2 / 4 bar uses [1, 2), [2, 4), and [4, max]. The dial labels include the quick stops and real range endpoints, adding spaced round values within the supported range. These are zoom shortcuts, not claims about optical lens magnification. A horizontal swipe starting on this bar opens a translucent circular dial centered at the current value. Swiping left increases zoom; fine logarithmic graduations follow finger travel beneath a fixed yellow index and live value. Input is incremental, so reversing at a limit responds immediately. Re-grabbing the arc adjusts from the current value without jumping. The dial has no expand/collapse buttons. It remains visible while a finger is down, then fades away one second after the last finger lifts or is cancelled. A tap during that interval dismisses it immediately; a dismissing tap within the preview does not also select a subject. Touches outside the preview also dismiss the dial. Timers are cancelled when the control is removed.

Pinching anywhere in the preview changes camera zoom and animates the preset bar into one centered live value without opening the dial. The single value remains until the last finger lifts or is cancelled, then the three slots animate back into place. Adding a second finger to an arc drag switches to pinch; lifting one finger does not reopen the dial. Preset taps set the exact target immediately without counting through intermediate values or expanding the dial. The selected capsule shares the bar’s height and corner radius, meeting its outer edge in either end slot. Both forms of adjustment respect the device range. The controls overlay the 3:4 viewfinder without changing its size. Preview, analysis frames and captured pixels use the same camera zoom. During a gesture the overlay follows local pointer updates independently of native acknowledgements, and zoom value notifications rebuild only the overlay. Every accepted value, including a subpixel change across a displayed rounding or slot boundary, reaches the camera so release cannot restore an older value. A delayed response to an earlier request cannot replace the newest pending target. Throughout an adjustment gesture the controller skips incoming samples and keeps only the newest zoom request; after a successful change it discards the prior frame, recommendation and stability hold while preserving the selected subject for reacquisition. Preview status text stays in the upper-right label. Front cameras do not query zoom limits, show the bar or dial, or accept pinch/zoom requests; switching back to a rear camera recomputes its range and stops. Unsupported or single-value rear-camera ranges hide the control. The practice image and Web mode do not expose camera zoom.

`camera_zoom_test.dart` covers dynamic stops and range endpoints, front/rear switching and rejected front-camera gestures, range mapping, serialized latest-value requests, device failures and reset invalidation, gesture boundaries, dismissal deadlines and cancellation, pinch/drag transitions, preset taps, and subject recovery after zoom changes.

## Where to make a change

The lower-right preview angle uses small, subdued off-white text with a light shadow and no panel, retaining the original upward/downward, level and left/right tilt labels with their corresponding degrees on one line. Sensor waiting, motion and unavailable messages retain priority. It fades out while the zoom arc is open to avoid overlapping edge graduations, and never intercepts preview taps. The guidance headline below the preview uses short, single-line copy with ellipsis; Direct capture uses the original compact row below the centered shutter only while not ready. When ready, that row disappears. Optional composition advice is hidden without reserving a row or extra spacing below the shutter. The guidance footer uses its natural height, and its largest centered 3:4 preview fills the remaining space. The mode tabs, More menu and full-screen photo viewer remain available.

For a selected subject, the one-second hold means the target center stays inside the visible tracking box (14% of preview width × 13% of preview height). The drawing and readiness check share these dimensions. Small movements within that box continue the timer and retain readiness; there is no separate per-frame displacement gate. Leaving the box, losing the subject, stale frames or strong sensor motion resets the hold. Horizon-only guidance keeps its line tolerance; tilt and composition quality remain advice.

## Photo filters

The filter control uses a small, thin-line overlapping-lens icon and the selected preset name below the viewfinder while framing and guiding. The recommendation view omits its filter shortcut row and keeps the composition choices in the footer. Camera switching remains in the upper-right header; the three-line More menu contains flash with its current state and Help, plus the filter control after selecting a Pose reference; the header has no photo shortcut. It offers Original, Warm Light, Clear, Film and Monochrome, with adjustable strength. `PhotoFilter` defines local color matrices from saturation, contrast and channel balance. Film adds deterministic procedural grain and a vignette; Monochrome adds a subtle vignette. Strength zero restores the original pixels when manual adjustments are neutral. Presets require no downloaded resources or additional permissions.

Only the photo layer passes through `FilteredPhoto`; guides and text retain their own colors. Tracking and composition continue to use the unfiltered camera samples. Preview and PNG export share the same recipe and normalized texture coordinates. Capture freezes that recipe; changing filters is disabled until the next shot. Saving retries reuse the captured PNG without applying the filter again. An in-flight capture invalidated by suspension cannot publish or save its result.

The same sheet also offers brightness, contrast, saturation and warmth. Their neutral value is zero, displayed on a −100 to +100 scale. These local adjustments compose after the preset's color matrix and before its texture; neutral adjustments preserve the existing preset output. They also work with Original or zero preset strength. Reset clears the four adjustments while keeping the selected style and its strength. All controls remain in the modal sheet, so they add no row below the viewfinder. The capture recipe includes these adjustments and saving retries retain them.

`photo_filter_test.dart` compares rendered preview and export pixels, checks zero strength, monochrome output, cropping/mirroring and save retries. Widget screenshots use the licensed sample image. Native camera textures, front/back camera orientation, gallery output, permission interruption and capture during backgrounding still require real-device verification on Android and iOS; widget rendering does not establish device color or performance parity.

## Generated content and assets

| Output | Source / generation |
| --- | --- |
| `assets/legal/`, `lib/services/policy_pages.g.dart` | `python3 tools/build_policy_pages.py` from policy text in that script and `policies/config.json` |

Operator, contact and consent revision are generated from `policies/config.json`. `policy_pages.g.dart` contains the HTML used by native and Web views. The app handles internal document links using the `frame-policy` URI scheme; selected GitHub/mail links open externally.

Do not patch generated policy output directly. Change the source, regenerate, and review the resulting copies together. See [local policy pages](../policies/README.en.md).

For new Chinese UI characters, inspect actual rendering. To rebuild the font, use a virtual environment with `fonttools`, then run `python tools/update_ui_font.py /path/to/NotoSansSC.ttf`. Keep the font license and inspect the diff; changing prose in Markdown does not require rebuilding the UI font.

Licenses for the bundled photo and documentation screenshots are listed in [Third-party notices](../THIRD_PARTY_NOTICES.md). Screenshots are presentation assets, not device-test evidence.
